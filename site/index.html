ksproxy

Lets an AI agent use your ssh servers, Kubernetes clusters, local folders, databases, queues, HTTP APIs and MCP servers without ever holding a credential, through a per-target allowlist that refuses everything by default.

npm install -g @ksproxy/cli

Node.js 24 or later, macOS and Linux, no npm dependencies.

  • npm

The problem

An agent that manages infrastructure normally needs your ssh keys or your kubeconfig. Once it holds them, it can do whatever the credential allows, and you find out afterwards, if at all. ksproxy keeps the credential on your side: you open the connections, and the agent gets only a narrow, logged tool interface.

  • No credential for the agent. You hold it; the agent only calls tools.
  • Default deny. A call that no rule allows is refused.
  • Everything is logged. You see each call as it happens, and read it later.
  • One Ctrl-C. It closes every connection and stops every proxy.

How it works

  1. You start it. Run ksproxy start in a terminal, pick the targets and leave it running. It opens the ssh connections (ssh may ask for your password or key passphrase in that terminal), the kubectl proxy processes and the other targets.
  2. The agent calls it. Your agent talks to the built-in MCP server, ksproxy mcp. Each call is checked against the target's allowlist and refused unless a rule allows it. With model review turned on for a target, a model can also approve a command that no rule matches.
  3. You watch. Every call and event appears in your terminal as it happens. Ctrl-C closes every connection and stops every proxy.

What the agent gets

Four MCP tools for ssh, Kubernetes and local targets, one more for each kind of service target, and the tools of each MCP server. A call times out after 1 to 600 seconds (default 60). Stdout and stderr are each capped at 256 KiB, and maxOutputKiB raises that for one target to at most 4096 KiB.

ToolWhat it does

local_execRuns an allowlisted command on your machine in a local target's folder: target, command, optional timeout_seconds. No shell is involved.

Local targets run a short list of commands in a folder on your own machine:

  • Folder checks. Opening only checks that the folder exists, can be resolved, and is not your home directory, the root, ksproxy's own folders or a folder holding an inventory kubeconfig.
  • Wildcards stay plain. A wildcard matches only plain names and paths, never a flag. Flags and anything else must be written literally in the rule. Each plain value, links followed, must stay inside the folder.
  • Outside files. A file outside the folder is reachable only if you write it literally into a rule (cat /etc/hosts).
  • Protected names. Paths you list in protect, and names that usually hold secrets, are never matched by a wildcard.
  • Listed programs. A programs list with a paths list lets the agent run the programs you name, with any arguments, as you, inside those paths. Name only programs you would let the agent use freely. See docs/LOCAL-TARGETS.md.

Databases, queues and HTTP APIs. ksproxy start holds the password or token and carries out each call, so the agent never sees it. Every call goes through a strict reader of its kind, fixed refusals that no rule can lift, and your allowlist.

  • postgres and mysql (also MariaDB): one SQL statement at a time, read-only by default.
  • mongodb: one command document, with results bounded.
  • redis: one command, over TCP or TLS.
  • elasticsearch and rabbitmq (management API): one HTTP request.
  • kafka: the Kafka command-line clients you installed.
  • http: any HTTP API, with a bearer token, basic auth or one header.
  • command: one client program that you name.

The rights of the account the target uses are the real boundary. The reference is docs/SERVICES.md.

MCP servers

The mcp kind lets the agent use the tools of an MCP server, local or remote, without holding its credential. ksproxy start starts the server, or connects to it, with the credential it holds.

{
  "mcp": [
    {
      "name": "jira",
      "description": "Jira of jira.example.com",
      "command": ["uvx", "mcp-atlassian@0.24.8"],
      "env": {
        "JIRA_URL": "https://jira.example.com",
        "JIRA_USERNAME": "someone@example.com",
        "JIRA_API_TOKEN": { "fromEnv": "JIRA_TOKEN" }
      },
      "allow": [
        "jira_get_issue",
        "jira_search",
        { "tool": "jira_add_comment", "arguments": { "issue_key": "regex(SHOP-[0-9]+)" } }
      ]
    }
  ]
}
  • Tools by name. Each allowed tool is in the agent's own tool list as TARGET__TOOL, for example jira__jira_get_issue. In a rule, write the server's own name for the tool (jira_get_issue).
  • Rules. A rule is a tool name, or an object with tool and the arguments values a call must match. "allow": "any" is refused. arguments on the target pins a value for every call.
  • Local or remote. command runs a local server (uvx, npx, pipx, bunx, docker run -i --rm or any program). url connects to a remote server over https, with no login, a bearer token or basic auth.
  • Secrets stay out of the file. In env, write { "fromEnv": NAME }. start holds that value and hides it everywhere.
  • Exact versions. A package run by npx, bunx, uvx, pipx or docker run must name an exact version or image tag, so that the code does not change without you.
  • Nothing new to learn. There is no new command and no new flag. Choose mcp targets in the picker or with --all, check a rule with ksproxy check mcp NAME TOOL [JSON], and see the server in ksproxy doctor.
  • Not supported yet. The browser OAuth login, and model review of mcp calls.

Read "What it does not do" below before you add a local server. The details are in docs/MCP-SERVERS.md and the README.

You decide what it may run

Targets live in ~/.config/ksproxy/inventory.json. Each has an allow list; a target with no allow refuses everything.

{
  "ssh": [
    {
      "name": "web1",
      "host": "web1.example.com",
      "description": "production web box",
      "allow": ["systemctl status *", "journalctl -u myapp ...", "df -h"]
    }
  ],
  "kubernetes": [
    {
      "name": "lab",
      "kubeconfig": "~/.kube/lab-agent.yaml",
      "proxyPort": 8001,
      "manifestRoots": ["~/projects/lab/manifests"],
      "description": "lab cluster",
      "allow": ["get ...", "describe ...", "logs ...", "rollout status ...", "apply -f *"]
    }
  ],
  "local": [
    {
      "name": "infra",
      "cwd": "~/projects/infra",
      "description": "terraform repo",
      "allow": ["git status", "git log --oneline -n * ...", "terraform plan", "ls -l ..."]
    }
  ]
}

A rule is whitespace-separated tokens matched against the command's arguments:

  • A literal matches an argument equal to it. df -h allows exactly df -h.
  • * matches exactly one argument that does not start with -. systemctl status * allows systemctl status nginx.
  • ... matches zero or more arguments of any shape, and only as the last token. journalctl -u myapp ... allows journalctl -u myapp --since today -n 50.

Before a rule is tried, fixed checks run that no rule can lift:

  • ssh. A command is split into tokens and every character is checked. Quotes, ; | & $, backticks, redirects, globs and newlines are refused outright, so no shell syntax reaches the remote host.
  • Kubernetes. Arguments pass a fixed verb-and-flag allowlist first. It refuses exec, port-forward, credential flags and secret resources whatever your rules say. Files given with -f must sit inside manifestRoots.

Examples: a read-only and a write target for each kind.

Try a rule without opening anything (for an mcp target, the kind word is mcp):

ksproxy check ssh web1 systemctl status nginx
ksproxy check kube lab get secrets
ksproxy check local infra git status
ksproxy check mcp jira jira_get_issue '{"issue_key":"SHOP-1"}'

Optional model review

When no rule matches a command, ksproxy can ask a model if it fits a policy you wrote.

  • Off by default. You turn it on per target, with any OpenAI-compatible provider. It is not available for mcp targets.
  • Refuses when unsure. Anything but a clean approval is a refusal, and the tool's reply does not show the model's reason.
{
  "reviewers": {
    "groq": {
      "baseUrl": "https://api.groq.com/openai/v1",
      "model": "<model id>",
      "keyEnv": "GROQ_API_KEY"
    }
  },
  "ssh": [
    {
      "name": "web1",
      "host": "web1.example.com",
      "allow": ["uptime", "df -h"],
      "review": {
        "reviewer": "groq",
        "policy": "read-only diagnostics, no restarts, no file contents"
      }
    }
  ]
}

The model judges the words of a command, not what it does, so keep write commands on the allow list. The review document lists every check and limit.

You see everything

  • Live. ksproxy start prints one line per agent call and per event. ksproxy log shows the same lines later.
  • Refusals explain themselves. A refused call shows a short reason; the agent receives the full explanation with the allowed rules.
  • Audit file. Every call is also kept as a JSON line in logs/audit.log in the state folder (command and decision, not output). The log is rotated at 5 MiB and the 5 newest old files are kept.
12:18:40 ssh  web1       OPENING         web1
12:18:41 ssh  web1       UP
12:18:43 --   session    READY           2 targets, pid 31973
12:19:19 ssh  web1       ok       0.1s   uptime
12:19:20 ssh  web1       DENIED          cat /etc/shadow  [not on allowlist]
12:19:23 kube lab        DENIED          get secrets -A  [secret resource]
12:41:00 --   session    CLOSING         Ctrl-C
12:41:01 --   session    CLOSED          3 calls: 1 ok, 0 failed, 2 denied

Quick start

Write a sample inventory. It never overwrites an existing file.

ksproxy init

Edit it: your own targets, and an allow list for each. Examples: a read-only and a write target for each kind.

$EDITOR ~/.config/ksproxy/inventory.json

Start a session, pick targets, and leave the terminal open. Ctrl-C ends it. Run it with the environment variables that your service and MCP targets name.

ksproxy start

If start fails, run the same line with doctor in place of start. start stops at the first problem; doctor shows all of them in one run. It opens each target the way a session does, runs one fixed read-only check of its kind, and changes nothing on a target. It exits 0 when every target is OK.

ksproxy doctor

Add the MCP server to your agent once. The summary printed by start shows the exact line; for Claude Code it has this shape:

claude mcp add ksproxy -- <node> --disable-sigusr1 <path to bin/ksproxy.js> mcp

Check the session at any time.

ksproxy status

More: projects and network access

  • Projects. --project NAME on every command but token gives a set of targets of its own (projects/NAME.json in the config folder) and a state folder of its own. Two agents in two repositories each see only their own targets, and sessions of different projects run at the same time. ksproxy start --project shop,ops --all runs several in one terminal. Without --project, nothing changes. See docs/PROJECTS.md.
  • Network access. By default ksproxy opens no network port. ksproxy start --listen HOST:PORT also serves the projects of that start over HTTP, at /mcp and /p/NAME/mcp, to an agent on another device of your network. The address must be a loopback or private IP address of this machine. One token opens every project of that start; ksproxy token shows its dates, never the token; ksproxy token revoke ends it. Plain HTTP is the default, and --tls-cert FILE --tls-key FILE turn on TLS. See docs/NETWORK-ACCESS.md.
  • A server behind another server. jumps on an ssh target reaches a server that only another server can reach. See docs/JUMPS.md.

What it does not do

The allowlist is a second lock; the first is that the agent never holds a credential. These limits matter when you decide what to allow. The full list is in the README and SECURITY.md.

  • The allowlist binds only the MCP path. An agent that also has an unrestricted local shell can use the ssh sockets and proxy ports directly.
  • Files it can edit. An agent that can edit the inventory or the session files can widen its own rules.
  • Your own user is not a wall. A process that runs as you and can inspect processes or read your files can reach the credentials that ksproxy start holds. Run the agent without a shell of your user, in a sandbox, or as another user. Projects do not change this.
  • Programs can do more than they say. A rule is only as safe as the program it allows. find ..., awk ..., vim, less and sudo ... can run other commands.
  • Output is not redacted. Command output is returned as-is. A program that prints a secret leaks it to the agent. Replacing local paths and proxy addresses in the output is not redaction.
  • Rights are the boundary. The remote user's permissions and Kubernetes RBAC remain the boundary. A workload the identity may create, such as a Pod that mounts a Secret or a service-account token, is not inspected by this tool.
  • Rules match words, not meaning. The rights of a database or service account are the real boundary, and a secret that a service returns in its own output reaches the agent. Only the credentials that ksproxy holds are hidden.
  • "allow": "any". On an ssh target the command is sent as written, so pipes and redirects work. "any" is an error for local, command, postgres, mysql, mongodb, kafka and mcp targets (and ssh targets with jumps).
  • A local command runs as you. It runs on the machine that holds your keys, so give local targets the shortest allow list of all. The folder check looks at arguments only: a program can still read other files by itself, and some programs (git, make, npm, terraform plan) run code they find in the folder. The full list is in docs/LOCAL-TARGETS.md.
  • Listed programs. A listed program that can act as you (an interpreter, ps, gh, aws, an archive program such as tar) gives the agent your whole account. ksproxy start and ksproxy check warn when you list one. The refused options of listed programs are a best effort.
  • Protected locations. They are those recorded by ksproxy start (its own state and configuration folders and every inventory kubeconfig), not whatever the agent host's environment says. Programs are found through the absolute entries of your PATH; relative entries and entries inside any local target's folder are dropped. A path is replaced whole in output, also when its letter case differs and where the output limit cuts the text.
  • Hard kills. After a SIGKILL or power loss, connections and proxies it opened can outlive it until the next ksproxy start closes them.
  • A local MCP server is third-party code, run as you, without a sandbox. It gets the credential it needs, and it can read your files and reach the sockets and proxies of this session. ksproxy's rules check what the agent asks, not what the server's code does. Read what a server does before you add it, and give it an account with only the rights the agent needs.
  • A rule cannot limit what a query reads. A pattern on a JQL, CQL or search string can be passed by a query that reads more. Rules choose tools and fixed values; the rights of the account limit the data.
  • A pin fixes the package, not its dependencies. An image tag can still be moved by whoever publishes it; only a digest fixes it. uvx --exclude-newer DATE fixes dependencies to a date.
  • A remote MCP server sees what the agent sends and decides what it answers. Its descriptions and answers can try to steer the agent, as any output can.
  • One token opens every project of a start --listen. Plain HTTP lets anyone who can record that network read the token and every answer, so use TLS on a shared network. The token does not say which device holds it.
  • Out of scope. Creating server users, sudoers rules, RBAC, tokens or kubeconfigs; file transfer; interactive shells; port forwarding for the agent; redacting secrets from output; Windows.

Reliable setups for the agent side are an agent with no general shell, or one whose shell runs in a sandbox that cannot read ~/.ksproxy or ~/.config/ksproxy and cannot reach local sockets and ports.
