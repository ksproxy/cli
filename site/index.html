ksproxy

Lets an AI agent use your servers, clusters, databases and MCP servers without ever holding a credential. Every call goes through an allowlist that refuses everything by default.

npm install -g @ksproxy/cli

Node.js 24 or later, macOS and Linux, no npm dependencies.

  • npm

The problem

An agent that manages infrastructure normally needs your ssh keys, your kubeconfig or your database password. Once it holds them, it can do whatever they allow. ksproxy keeps them on your side: you open the connections, and the agent gets only a narrow, logged set of tools.

  • No credential for the agent. You hold it; the agent only calls tools.
  • Default deny. A call that no rule allows is refused.
  • Everything is logged. You see each call as it happens, and can read it later.
  • One Ctrl-C. It closes every connection and stops every proxy.

How it works

  1. You start it. Run ksproxy start in a terminal, pick the targets and leave it running.
  2. The agent calls it. Your agent talks to the built-in MCP server. Each call is checked against the target's allowlist and refused unless a rule allows it.
  3. You watch. Every call appears in your terminal as it happens. Ctrl-C ends the session.

What the agent can reach

TargetWhat a call is
ssh serversOne command, with no shell syntax. A server behind another server works too.
Kubernetes clustersOne kubectl call through a local proxy. exec, port-forward and secrets are always refused.
Local foldersOne listed command inside a folder on your machine.
Databasespostgres, mysql, mongodb, redis: one statement or command, read-only by default where the kind has it.
Queues and searchkafka, rabbitmq, elasticsearch.
HTTP APIs and programshttp: any API with a token or basic auth. command: one client program that you name.
MCP serversThe tools you allow of any MCP server, local or remote, under the name TARGET__TOOL.

Each kind has its own page: examples for every kind, local targets, databases, queues and HTTP APIs, MCP servers.

You decide what it may run

Targets live in ~/.config/ksproxy/inventory.json. Each has an allow list; a target with no allow refuses everything.

{
  "ssh": [
    {
      "name": "web1",
      "host": "web1.example.com",
      "description": "production web box",
      "allow": ["systemctl status *", "journalctl -u myapp ...", "df -h"]
    }
  ]
}
  • A plain word matches itself: df -h allows exactly df -h.
  • * matches one argument that is not a flag: systemctl status * allows systemctl status nginx.
  • ... at the end matches any further arguments.

Fixed checks run before any rule and cannot be lifted by one. Try a rule without opening anything:

ksproxy check ssh web1 systemctl status nginx

More in the rules page. A model can also review a command that no rule matches, if you turn that on: model review.

You see everything

ksproxy start prints one line per call. ksproxy log shows the same lines later, and every call is kept in an audit file.

12:18:41 ssh  web1       UP
12:19:19 ssh  web1       ok       0.1s   uptime
12:19:20 ssh  web1       DENIED          cat /etc/shadow  [not on allowlist]
12:19:23 kube lab        DENIED          get secrets -A  [secret resource]
12:41:01 --   session    CLOSED          3 calls: 1 ok, 0 failed, 2 denied

Quick start

  1. Write a sample inventory, then put your own targets and rules in it. 
    ksproxy init
  2. Start a session, pick targets, and leave the terminal open. 
    ksproxy start
  3. Add the MCP server to your agent once. start prints the exact line for it.

If start fails, run ksproxy doctor with the same arguments: it checks every target and shows every problem in one run. The README has the full steps.

What it does not do

The allowlist is a second lock; the first is that the agent never holds a credential. Know these limits before you decide what to allow.

  • The rules bind only the MCP path. An agent that also has a shell of your user can reach the connections, the files and the credentials directly. Run the agent without a general shell, in a sandbox, or as another user.
  • Rights are the real boundary. Rules match words, not meaning. What the remote user, the Kubernetes role or the database account may do is what limits the agent.
  • A rule is only as safe as the program it allows. find, awk, vim, git and sudo can run other commands.
  • Output is returned as it is. Only the credentials that ksproxy holds are hidden in it. A secret that a program or a service prints reaches the agent.
  • A local command or a local MCP server runs as you, without a sandbox. Give local targets the shortest allow list of all.

The full list is in SECURITY.md.
